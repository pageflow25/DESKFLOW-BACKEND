# Projeto: Plataforma de gerenciamento de motoboys



Escopo definido

MVP — até 10 motoboys



Minha recomendação é desenvolver uma plataforma própria de gestão de entregas, com foco em simplicidade operacional, controle financeiro e facilidade de expansão.

O sistema terá dois ambientes principais:

- Administrativo: você controla motoboys, entregas, distribuição, pagamentos e indicadores.
- Motoboy: o entregador acessa pelo celular, visualiza suas entregas, aceita serviços e atualiza o andamento.

Não desenvolveria um marketplace neste primeiro momento. Como você terá sua própria equipe e o cadastro será administrativo, podemos construir uma solução muito mais enxuta.

Vou estruturar o projeto pensando em uma operação inicial de até 10 entregadores, mas sem limitar o crescimento futuro.

# 1. Arquitetura da aplicação

## Arquitetura geral

Painel administrativo

React + Vite · Desktop e mobile

Aplicação do motoboy

React + PWA · Mobile

HTTP / REST API · WebSocket

Backend central

Node.js + Express + Sequelize

Autenticação · Regras de negócio · Serviços · Eventos

PostgreSQL

Dados operacionais

Armazenamento

Fotos e comprovantes

Serviços externos

Google Maps · Geocodificação · Notificações

## Stack tecnológica

| Camada              | Tecnologia                                |
| ------------------- | ----------------------------------------- |
| Frontend            | React + Vite                              |
| Interface           | Tailwind CSS                              |
| Backend             | Node.js + Express                         |
| Banco de dados      | PostgreSQL                                |
| ORM                 | Sequelize                                 |
| Autenticação        | JWT + cookies HTTPOnly                    |
| Tempo real          | Socket.IO                                 |
| Mapas               | Google Maps API                           |
| Aplicativo          | PWA                                       |
| Hospedagem frontend | Vercel                                    |
| Hospedagem backend  | Render                                    |
| Arquivos            | S3 compatível ou armazenamento de objetos |

Uma decisão importante: não criaria dois backends. O painel administrativo e o aplicativo dos motoboys consumirão a mesma API, com autenticação e permissões diferentes.

Também não utilizaria microserviços no início. Um monólito modular é suficiente para essa escala e facilita manutenção.

## Organização do backend

```
src/
├── config/
├── database/
├── middlewares/
│   ├── auth.middleware.js
│   ├── permission.middleware.js
│   └── error.middleware.js
│
├── modules/
│   ├── auth/
│   ├── usuarios/
│   ├── motoboys/
│   ├── veiculos/
│   ├── entregas/
│   ├── distribuicao/
│   ├── financeiro/
│   ├── localizacao/
│   ├── notificacoes/
│   └── dashboard/
│
├── sockets/
├── shared/
├── routes/
└── app.js
```

Cada módulo terá sua separação de responsabilidades:

- `routes`: definição dos endpoints.
- `controllers`: recebimento e resposta das requisições.
- `services`: regras de negócio.
- `repositories`: acesso aos dados.
- `models`: entidades Sequelize.
- `validators`: validações de entrada.

A distribuição automática será uma regra de negócio do módulo `distribuicao`, não uma responsabilidade do controller.

# 2. Escopo funcional do MVP

O MVP deve resolver a operação diária sem depender de processos manuais paralelos.

Obrigatório no MVP

| Módulo       | Funcionalidades                          |
| ------------ | ---------------------------------------- |
| Autenticação | Login, logout, recuperação de senha      |
| Usuários     | Administrador e motoboys                 |
| Motoboys     | Cadastro, edição, ativação e desativação |
| Veículos     | Cadastro de moto e documentação básica   |
| Entregas     | Criar, editar, cancelar e consultar      |
| Distribuição | Manual e automática                      |
| Aplicativo   | Aceitar, recusar e atualizar entregas    |
| Financeiro   | Valor por entrega e fechamento           |
| Histórico    | Registro de todas as alterações          |
| Dashboard    | Indicadores operacionais e financeiros   |

## 2.1. Cadastro de motoboys

O administrador poderá cadastrar:

- Nome completo.
- CPF.
- Telefone.
- E-mail.
- Endereço.
- Data de nascimento, se necessária à operação.
- Foto de perfil.
- Dados da motocicleta.
- Placa.
- Modelo.
- Situação cadastral.
- Valor padrão por entrega.

Cada motoboy terá um usuário para acessar o aplicativo.

Estados cadastrais:

- Ativo.
- Inativo.
- Bloqueado.

Também terá um estado operacional separado:

- Disponível.
- Ocupado.
- Offline.

É importante não misturar situação cadastral com disponibilidade operacional.

## 2.2. Cadastro de entregas

Campos principais:

| Campo                | Descrição                |
| -------------------- | ------------------------ |
| Código               | Identificador da entrega |
| Cliente              | Nome de quem solicitou   |
| Telefone             | Contato do cliente       |
| Endereço de retirada | Local da coleta          |
| Endereço de destino  | Local de entrega         |
| Observações          | Instruções               |
| Valor da entrega     | Valor cobrado            |
| Valor do motoboy     | Valor que será pago      |
| Motoboy              | Entregador responsável   |
| Prioridade           | Normal ou urgente        |
| Data prevista        | Prazo de entrega         |

Eu separaria o valor cobrado do cliente do valor pago ao motoboy. Isso permitirá calcular o resultado financeiro real da operação.

## 2.3. Distribuição das entregas

Você terá dois modos:

Manual

O administrador seleciona uma entrega e escolhe o motoboy.

Automático

O sistema seleciona um entregador elegível considerando:

1. Se está online.
2. Se está disponível.
3. Quantidade de entregas em andamento.
4. Distância até o endereço de retirada.
5. Tempo estimado para chegar ao local.

Para o MVP, começaria com uma distribuição automática simples, por disponibilidade, carga de trabalho e distância. Não tentaria implementar inteligência artificial ou otimização complexa de rotas.

O motoboy receberá uma solicitação e terá um prazo para aceitar. Caso recuse ou não responda, a entrega retorna para distribuição.

### Regras importantes do banco

Eu implementaria desde o começo:

- UUID como identificador principal.
- Chaves estrangeiras e índices.
- `DECIMAL(10,2)` para valores financeiros, nunca `FLOAT`.
- Transações nas operações de distribuição e pagamento.
- Histórico imutável das mudanças de status.
- Soft delete apenas onde fizer sentido.
- Unicidade para impedir que uma mesma entrega seja paga duas vezes.
- Pagamentos associados às entregas específicas, evitando duplicidade de quitação.

Uma decisão especialmente importante: o valor do motoboy deve ser congelado no momento da conclusão da entrega. Se você alterar o valor padrão do entregador futuramente, isso não poderá modificar o histórico financeiro de entregas antigas.

## 5.1. Comunicação em tempo real

Utilizaria Socket.IO para:

- Notificar o motoboy de uma nova entrega.
- Atualizar o painel quando uma entrega mudar de status.
- Atualizar a disponibilidade do entregador.
- Atualizar o mapa com novas localizações.

Exemplo de eventos:

```
// Administrador atribuiu uma entrega
entrega:atribuida

// Motoboy recebeu a solicitação
entrega:nova

// Motoboy aceitou
entrega:aceita

// Entrega atualizada
entrega:atualizada

// Localização atualizada
motoboy:localizacao

// Motoboy ficou online/offline
motoboy:disponibilidade
```

A API REST continuará sendo responsável pelas operações. O Socket.IO servirá para propagar atualizações, não para substituir as regras de negócio.

# 6. Regras de negócio essenciais

Antes de começar a desenvolver, definiria estas regras:

| Situação            | Regra                                                          |
| ------------------- | -------------------------------------------------------------- |
| Motoboy offline     | Não recebe distribuição automática                             |
| Motoboy ocupado     | Pode receber nova entrega somente se a operação permitir       |
| Entrega recusada    | Retorna para distribuição                                      |
| Entrega aceita      | Não pode ser atribuída a outro motoboy sem reatribuição formal |
| Entrega concluída   | Gera lançamento financeiro                                     |
| Entrega cancelada   | Não gera pagamento automaticamente                             |
| Pagamento realizado | Não pode ser contabilizado novamente                           |
| Motoboy inativo     | Não pode aceitar novas entregas                                |

Também criaria uma máquina de estados para impedir transições inválidas.

Por exemplo, uma entrega concluída não poderá voltar para o status de aguardando motoboy por uma simples requisição.

Para a distribuição automática, utilizaria transações e bloqueio de registros no PostgreSQL para evitar que dois administradores ou processos atribuam a mesma entrega simultaneamente.

# 8. Segurança e infraestrutura

Não deixaria esses pontos para depois:

- Senhas com hash seguro (bcrypt ou Argon2).
- Cookies HTTPOnly e proteção CSRF quando aplicável.
- RBAC para separar administrador e motoboy.
- Validação de todos os dados recebidos.
- Rate limiting e Helmet.
- Logs de operações importantes.
- Proteção de documentos e comprovantes.
- Backup automático do PostgreSQL.
- Controle de acesso às localizações.
- Localização coletada apenas durante o período operacional autorizado.

Também evitaria armazenar histórico de GPS indefinidamente. Para o início, podemos manter a última localização e um histórico com retenção definida.

# 9. O que não desenvolveria agora

Para não transformar o MVP em um projeto muito grande, deixaria para versões futuras:

| Funcionalidade                            | Versão |
| ----------------------------------------- | ------ |
| Otimização inteligente de rotas           | V2     |
| Aplicativo nativo Android/iOS             | V2     |
| Integração com WhatsApp                   | V2     |
| Portal para clientes                      | V2     |
| Múltiplas empresas/unidades               | V2     |
| Inteligência artificial para distribuição | V3     |
| Integração com gateways de pagamento      | V3     |

O PWA já atenderá a necessidade inicial do motoboy, e você poderá evoluir para aplicativo nativo quando houver demanda.

## 11. Decisões que precisamos fechar antes de codificar

Existem quatro detalhes que podem mudar algumas decisões da modelagem e do desenvolvimento:

1. Nome da plataforma: será XUA Delivery ou terá outra marca?
2. Origem das entregas: você vai cadastrar todas manualmente ou também precisará receber solicitações de clientes/estabelecimentos por integração?
3. Cobrança: você quer registrar quanto cobra do cliente e quanto paga ao motoboy, acompanhando o lucro de cada entrega?
4. Rastreamento: precisa visualizar a localização do motoboy em tempo real durante a entrega ou basta acompanhar os status?

Minha sugestão é manter a primeira versão simples, mas com uma estrutura que permita adicionar essas funcionalidades sem precisar reconstruir o sistema.

Próximo passo: posso transformar esse planejamento em um documento técnico de implementação, com especificação de cada módulo, migrations, relacionamentos, contratos de API e critérios de aceite, pronto para orientar o desenvolvimento com Claude Code.

Se quiser, também posso acompanhar o avanço do projeto semanalmente e organizar as próximas entregas de desenvolvimento.
